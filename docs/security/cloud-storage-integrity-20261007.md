## Behavior and donor adoption

The predecessor returns the first initialized Firebase app even when it belongs to another estate project. This repair uses a named Factory app and checks its project and bucket on every access. The dedicated and generic project settings must agree; known shared/other-entity projects are denied. `asset-factory-dev-id` remains a development target and is denied in production, matching the existing production deployment wrapper. A default bucket must name the exact configured project. This validates configuration consistency, not provider ownership. Custom buckets require a reviewed ownership/boundary contract and a corresponding source change; an arbitrary bucket-name override cannot bypass the boundary.

The declared long-lived credential-variable gate is deliberately adopted from preserved #273. Unlike that predecessor, this version applies it before cache reuse. It also refuses declared or well-known ADC JSON using service-account keys, authorized-user refresh tokens or malformed federation envelopes; external-account declarations are read with a 64 KiB limit and admitted only as configuration. A cached named app must carry the same SDK `applicationDefault()` credential object as well as the matching project and bucket. SDK initialization errors use a fixed diagnostic. The local environment template no longer suggests installing a private key. Production missing or refused Firebase authority fails closed; it cannot silently select the development JSON fallback or substitute Firebase emulator hosts, including the Storage SDK's direct `STORAGE_EMULATOR_HOST` alias.

Calling `applicationDefault()` and checking an external-account envelope does not prove a deployed identity, issuer, key-free custody, token exchange, IAM scope or independent process provisioning. SDK credential objects may contain historical in-process state; acceptance requires a freshly provisioned process and actual authenticated identity/build readback. Source configuration alone never creates that provider proof.

The predecessor overwrites a versioned object without a generation precondition. Generated writes now snapshot the caller's bytes, calculate CRC32C with the existing SDK validator, attach that checksum for server validation, preserve client CRC32C validation, and use `ifGenerationMatch:0`. The upload File also carries that default precondition, fencing the SDK's own checksum-failure cleanup. A corrupt response cannot cause an unconditioned delete of a later unrelated generation.

An existing object is reused only when MIME, size, checksum and the generation-pinned bytes agree with the requested SHA-256. Legacy same-byte objects can be adopted without a metadata overwrite. Different bytes or MIME at the same version fail. A new version/path is required for deliberately changed assets. Lost-response retries can reuse the verified object; there is no application retry loop or cleanup deletion. SDK writes retain its bounded default retry policy and use a 60-second request timeout. Actual locked defaults were inspected: at most 3 retries and a 600-second total retry cap. These settings are not spend authority.

Metadata uses the existing SDK's cancellable REST stream with explicit 60-second request/absolute application deadlines, zero metadata retries, strict HTTP-200 acceptance and a 64 KiB response ceiling. A stalled metadata request cannot block caller acceptance indefinitely or lead to an artifact read. Reads capture exact generation metadata, refuse unsupported or malformed encoding/identity, pin that generation, and stream bytes with an absolute 60-second cancellation timer. They refuse overlong/short content before returning bytes and compare CRC32C plus stored SHA-256 when present. Stream destruction and synthetic transport exercise the source cancellation request; they do not prove real auth/socket/provider cancellation. The 512 MiB ceiling preserves the existing governed video limit; client-upload Firebase rule limits remain unchanged. Completed but unverified objects stay private and unpublished. This lane performs no destructive cleanup or automatic recovery of historical objects.
